# Security review — 2026-08

Scope: `gh-agile` at commit `f296f62` plus the working tree, `templates/`, and the
`.github/` workflow and profile. Three independent reviews were run on a
different model, one per lens (complexity/cost, robustness, roles and
permissions); the permission-relevant findings are consolidated here and every
code claim below was traced by hand afterwards. Where a claim was **not**
verified, it says so.

## Threat model, stated so the severities mean something

This is a local CLI with no server, no network listener and no credential of its
own. Nothing here is remotely exploitable, so the realistic risks are narrower
and all three are about *trust boundaries the tool does not know exist*:

1. **Disclosure** — private board contents (story points, priorities, assignees,
   status history) reaching somewhere they should not.
2. **Misreported authorization** — a permission failure presented as success, so
   the operator believes a state that does not hold.
3. **Wrong target** — a write landing on a repository or project other than the
   intended one.

Severities are assigned against that model, not against a generic checklist.

---

## What is sound, and should not be disturbed

Recorded because a security review that lists only problems invites someone to
"fix" the parts that are right.

- **The tool never sees a credential.** Every authenticated call shells out to
  `gh`, which owns the token. No command takes a `--token`, nothing reads
  `GH_TOKEN`, and no code path stores, logs or forwards one. *Verified by
  reading every `subprocess.run` and `gh()` call site.*
- **The checked-in profile holds no secrets.** `.github/agile.json` is project
  numbers, keys, board definitions and a sprint cadence. It is meant to be
  visible and there is nothing in it that should not be.
- **Export output is gitignored.** `.gitignore` covers `exports/` and
  `.gh_agile_export.json`, so a full board dump does not become a commit by
  accident.
- **`templates/issue-adopt.yml` triggers on `issues:`, not
  `pull_request_target:`.** That is the right choice and it avoids the classic
  Actions secret-leak, where a privileged token is exposed to code from a fork.
- **GraphQL is built with variables, and every interpolation is escaped or
  validated.** Iteration titles go through `json.dumps` (there was once a bug
  where a value containing a quote rewrote the mutation around it); dates and
  durations are validated as ISO dates and bounded integers first. The reviewer
  looked specifically for unguarded interpolation and found none. The queries
  added this month interpolate only static query text — a root name (`user` /
  `organization`) and a field selection constant — never user input.
- **`require_graphql_budget`** refuses a destructive write when the budget
  cannot cover the repair. It is the model the permission preflight below should
  copy: name the concrete cost, refuse before the point of no return, say what
  to do next.

## Findings

### S1 — A permission failure on labels is reported as success · High · **fixed 2026-08-21**

`gh-agile:1026` (`cmd_setup`) and `gh-agile:1075` (`ensure_labels`).

```python
state = "created" if result.returncode == 0 else "already exists"
```

Every non-zero exit becomes `"already exists"`. A `403` from lacking push access
is therefore printed as convergence, and `setup` reports a full run having
created nothing. `ensure_labels` is worse: it discards the result entirely and
checks no return code at all, so a permission failure there is completely
silent until `create_issue --label` later references a label that was never
made.

The conflation was deliberate for the exists case — `gh label create` does exit
non-zero when the label is already present, and there is a comment saying so —
but it was never narrowed to *that* case.

This is finding type 2: the operator is told a state that does not hold.

**Fixed** by `create_label`, which matches the measured "already exists" stderr
and treats every other non-zero exit as the failure it is. `ensure_labels` now
goes through it, so it can no longer discard a result. A per-run set of confirmed
labels also stops `sync --adopt` re-attempting the same `key:` label once per
issue.

It proved itself within the hour. A `make self-test` run against the sandbox hit
`HTTP 403: API rate limit exceeded` on `gh label create` and stopped, naming the
reason — where the old code would have printed `label 'type:epic' already exists`
and carried on to fail somewhere less obvious.

That same run showed the fix's own first version was guilty of the thing this
review complains about: it asserted "you need push access" at a failure that was
a rate limit. A 403 covers both. The message now reads the reason before
explaining it, and there is a test for each branch.

### S2 — `epic` and `story` leave an undisclosed issue when the project write is refused · High · **fixed 2026-08-21**

`gh-agile:1346` (`cmd_epic`), `gh-agile:1381` (`cmd_story`).

Both create the issue, apply the title prefix, and — for a story — link it as a
sub-issue of its epic. Only then do they call `add_to_project`, which
`sys.exit`s on failure. The `print` of the issue number and URL come *after* that
call.

Any authenticated user can open an issue on a public repository with issues
enabled; writing to the owner's project is a separate grant. So this is the
default outcome for an external contributor: a real, labelled, retitled,
parented issue exists, and the tool exits without telling them its number or its
URL. Issue numbers are never reused, so it is a permanent orphan nobody knows to
close.

**Fixed.** Both commands now print the number and URL as soon as the issue
exists, and wrap the board writes in `board_write_reported`, which turns any
failure into:

```
issue #41 was created at https://github.com/o/r/issues/41
  but could not be put on project #4: gh project item-add failed: HTTP 403
  The issue is real and is not on the board. Either ask someone with
  project write to run `gh agile sync --adopt`, or close #41.
```

It re-raises anything that is not a `SystemExit`, so a genuine bug still
surfaces as a traceback rather than being reported as a permission problem.

### S3 — `--owner` defaults to the caller, so a project number can resolve to the wrong project · High · *verified*

`gh-agile:3234`, and the absence of any `project.owner` key in the profile
schema.

`--owner` defaults to `@me`, resolved to the authenticated caller's own login.
The profile records `project.number` and never records whose project it is. So
`project.number: 4` means "project 4 belonging to whoever typed this".

For a non-owner the benign outcome is "no project 4 found". The harmful one is
that they happen to own an unrelated project 4 — and then `sync --adopt`, whose
default `--limit` is 200, labels issues onto it. `apply_defaults` already refuses
a `--project` that disagrees with the profile, on the reasoning that it is
"almost always the right flag in the wrong clone"; the same care was never
extended to the owner, which is the more likely mistake for anyone who is not
the owner.

**Fix:** record `project.owner` at `project create` time and default `--owner`
from it before falling back to `@me`. One profile field. It also makes the
read-only commands usable by other roles, which is the S6 half of the same
change.

### S4 — `config_from` cannot distinguish "no profile" from "no read access" · Medium · *verified*

`gh-agile:631`.

Every candidate path failing produces one unconditional message: *"points at X,
which has no profile"*. GitHub answers an unauthorized read with `404` rather
than `403`, precisely so that existence is not leaked — so a caller without
access to the main repository is told confidently that the profile is not there
when it is.

The security consequence is mild (the tool is *more* discreet than intended, not
less) but the usability consequence is not: it sends someone to create a profile
that already exists, and a second profile is a second source of truth.

**Fix:** inspect the HTTP status and word the two cases differently.

### S5 — `export` in a `pull_request` workflow would disclose a private board · Medium · *not present in this repo; documentation gap*

`export` emits every field value, assignee, and the full status history for every
item. Nothing in the tool or the guide warns against running it from a workflow
triggered by `pull_request` with a broadly-scoped token, which would place a
private board's contents into a build log any contributor can read.

No such workflow exists here — the only shipped automation is correctly
triggered (see "What is sound"). This is recorded so it stays that way.

**Fix:** one line in `USER_GUIDE.md`'s automation section, and keep `export` out
of any fork-reachable trigger.

### S6 — No authorization preflight; every permission failure is a raw `gh` error · Medium · *verified*

`gh-agile:163` is the single generic exit for every failed `gh` call:

```python
sys.exit(f"gh {' '.join(args[:2])} failed: {result.stderr.strip()}")
```

Nothing checks `gh auth status`, the token's scopes, or `viewerPermission` before
a write. Delegating *authentication* to `gh` is correct and must stay; the gap is
that *authorization* is nobody's job, so a missing `project` scope — common,
because `repo` does not imply it — is discovered partway through a write rather
than before it. S2 is the sharp edge of this.

**Fix:** a preflight built from reads that cost nothing and touch no token:
`gh auth status` for scopes, one project read, and `gh repo view --json
viewerPermission`. Refuse with the missing permission named and the command that
grants it (`gh auth refresh -s project`).

### S7 — `sync --adopt` has a wide default blast radius and no confirmation · Medium · *defaults verified, full path not traced*

`--state open`, `--limit 200`, no required dry-run, no count confirmation. This
command has already once swept every issue in a live repository onto a scratch
project and labelled all of them; that incident is recorded in
`docs/lessons.md`. The tool refuses before less consequential acts
(`require_graphql_budget`, the Makefile teardown guard), so the posture is
inconsistent.

**Fix:** print the count and require `--yes` above a small threshold.

### S8 — Organization-owned projects are not known to work · Medium · *found while rewriting `fields_of`; not verified against a live org*

`fetch_items` catches `SystemExit` per root when trying `user(login:)` then
`organization(login:)`, because `gh` exits non-zero when GraphQL returns an
`errors` block — which is what asking the wrong root does. `project_id`
(`gh-agile:~907`) and `sprint_field` do **not** catch it. If the error path is
what an org login actually takes, those two exit on the first root and never
reach the organization fallback, meaning most write commands would fail against
an org project.

`project_fields`, added this month, catches it. The other two were left alone
deliberately: changing them blind would be reasoning about GitHub instead of
measuring it.

**Fix:** stand up an org in the sandbox and measure which branch is taken, then
make all four consistent. This gates the Organization half of the README's Team
Usage section.

### S9 — Making the board public discloses more than the issues do · Informational

Not a defect — a consequence worth stating once. A public repository exposes
issue titles, bodies and comments. Making the **project** public additionally
exposes story points, priority, sprint assignment, and — through the export
anyone can then reproduce — the full status history and the cycle times derived
from it. That is an estimate-accuracy record about named people.

Current state, measured 2026-08-20: `paulcaron16k/gh-agile` is **private** and
project #4 is `public: false`. Read it from GraphQL rather than the UI:

```bash
gh api graphql -f query='{user(login:"OWNER"){projectV2(number:4){public}}}'
```

### S10 — Concurrent profile writes lose one · Low · accepted

Every profile write is a read-modify-write with no lock, so two concurrent runs
lose one of them. **The owner reviewed this and accepted the risk — do not
change it without asking.** The profile is checked in, so git is the recovery
path. Separately, the writes are not atomic (`write_text` truncates first), so a
process killed mid-write leaves a partial file; `read_config` detects that and
says so rather than misbehaving. `os.replace` would remove it.

## Not findings

- **The six sprint workarounds.** All three reviewers were invited to dispute the
  measurement behind them and none did.
- **Single-file layout, standard library only, labels as the carrier for
  type/key/sprint.** Constraints with recorded reasons, not oversights.

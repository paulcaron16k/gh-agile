# gh-agile v0.6.0 — on PyPI, with a front page worth reading

**The first build published to PyPI** (AGILE-314). `pipx install gh-agile` gives
the same single file the extension runs, as a tagged release that also works
standalone as `gh-agile`; `gh-agile install` links it into `gh`. The extension
still tracks `main`, so `gh extension upgrade agile` already brings everything
below; this tag is the package.

## gh-agile on PyPI

```bash
pipx install gh-agile
gh-agile install          # link it into gh, so `gh agile` runs it too
```

**The package is the same single file the extension runs** -- no dependencies,
no module -- shipped as a script, so the two routes differ in when a fix arrives
and never in what it does. `gh` runs only what is in its own extensions
directory, so **`gh-agile install`** is new: it links the installed copy in as a
local extension, and refuses to replace an `agile` `gh` already has. REFERENCE.md's
*Versions, and what installing gets you* now describes both routes, and says the
extension, not the package, is the one not to pin.

**`--version` names a package's version** -- `gh-agile 0.6.0  (package)` -- read
from its metadata. Before, a copy outside its own checkout either said `unknown`
or, inside a project's `.venv`, reported that project's `git describe` as its own.

**Fixed while packaging: a long install path broke the tool.** When an
interpreter's path is too long for a shebang, pip and uv write a `/bin/sh`
trampoline ahead of the script, and the script's `from __future__` import was
then no longer first -- a SyntaxError on every run. The import is gone, and
`tests/test_install.py` compiles the file behind a trampoline.

**`init --key` works on a fresh clone** (AGILE-313). It looked the key up in a
profile that did not exist yet and refused with *no repository for key*, in the
one place `init` exists for; it now uses the clone. `key add --config PATH`
creates a profile that is not there yet instead of raising.

**The README is now the PyPI front page** (AGILE-315): 420 lines, with a worked
example, a story's life cycle and the boards generated by the real commands. The
reference half moved to REFERENCE.md.

## What changed spelling

| Was | Is | Stage |
|---|---|---|
| Every spelling v0.4.0 retired: `epic`/`story`/`task TITLE`, top-level `move`, `set`, `fix` and `plan`, `validate --id`, `board show`, `setup`, `hooks`, `project create`/`owner`/`sprint-template`/`title-prefix`, bare `key` and `key --key`, `export --csv`/`--state`/`--grain both`, `sync --query`, bare `--add-assignee` | See [v0.4.0's note](release-v0.4.0.md) | Removed |
| `--format json` on a list, view or status (retired in v0.5.0) | `--json [fields]`, with `-q/--jq` and `-t/--template` | Removed |

**The hints are gone** (AGILE-307), as the v0.4.0 and v0.5.0 notes said they
would be. Each old spelling still fails at argument parsing, before anything
runs, and none is reinterpreted as something else; it now fails like any other
typo, with the command's usage rather than a line naming the replacement.

## What changed behaviour

**`validate` checks the `initiative:` label against the sub-issue tree** (AGILE-309),
in both directions: an issue in an initiative's tree without the label, and a label
on an issue that has left the tree. Both are problems, so **a board that passed
before can now fail** -- typically stories created before story create began
stamping the label, or issues given a parent in GitHub's web UI. `initiative
reconcile <slug>` fixes them; each finding names it. Where the parent chain leaves
the board, the label is a note that it cannot be checked, never a failure.

**`github_issues.initiative_slug` is read from the hierarchy, not the label**, and
is now nullable: empty when the issue is under no initiative, null when the parent
chain leaves the board before it can tell. It used to be blank wherever the label
had drifted. CSV writes both as empty; `github_catalog.json` states the type.
`board view --filter initiative:` still reads the label, so it agrees with the
saved board GitHub evaluates.

**`sync` adds missing `initiative:` labels** (AGILE-309) to the board's issues in
the repositories it covers, from the sub-issue tree. Additive only; silent when
nothing is missing; `--dry-run` reports them. A stale label is still
`initiative reconcile`'s to remove.

**`initiative reconcile` has no caps** (AGILE-309): the tree is paged past 100
children at a level, and the search for labelled issues past 200.

**The post-merge hook names `initiative reconcile`** for an issue the merge closed
whose label disagrees with its tree, on a report of its own, instead of folding it
into *the board has not caught up* with `issue close` as the fix. Still read-only.

## Security review

Done before the tag, per `docs/releasing.md` §3a, against the wheel and sdist
built from `main` at the release commit. **All eight pass.**

| # | Check | Result |
|---|---|---|
| 1 | No credential is handled | No read of `GH_TOKEN`, `GITHUB_TOKEN`, an `Authorization` header or a password in `gh-agile`; `gh` owns the token |
| 2 | No credential-shaped literal ships | None in the wheel or the sdist (`ghp_`, `github_pat_`, `gho_`, `AKIA`, private keys) |
| 3 | Nothing confidential ships | No internal names or hostnames; no email address; the only hosts are github.com, img.shields.io, jqlang.org and apache.org. The sample project is the fictional Widgets |
| 4 | No shell | No `shell=True`; every subprocess is an argument list |
| 5 | Destructive defaults unchanged | Live Makefile targets default to the sandbox; the teardown, sandbox and iteration-write tests pass |
| 6 | `install` writes only its own link | `tests/test_install.py` passes: refuses a checkout, a clone and somebody else's link |
| 7 | The wheel is the script | `gh-agile` and its metadata, nothing else |
| 8 | Published without a secret | `tests/test_publish_workflow.py` passes: OIDC only, `id-token` on the publish jobs, actions pinned to commits, PyPI from tags only |

**Not rehearsed on TestPyPI.** The rehearsal run built the wheel and was refused
there (`invalid-publisher`): trusted publishing is registered on PyPI only. The
build step it exercised is the same one the tag runs.
